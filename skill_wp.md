# WordPress REST Publishing

## When to use
- User gives a WP site URL + username + app password and asks to publish posts.
- Multi-article batches where each article carries SEO metadata (combined title options, meta description, categories, tags, focus keyphrase, slug).
- Tasks fixing dead internal links with a sitemap, or mapping requested categories/tags to what exists on the site.
- **Featured-image work of any kind**: setting/backfilling hero images, sourcing free images for articles that have none, or **reusing an image already in the site's media library** ("use the same image on karmactive" — see the media-reuse section, and never re-upload a duplicate).

## Core workflow
1. **Verify auth + discover the REAL taxonomy first.** `GET /wp-json/wp/v2/categories?per_page=100` and tags. Do NOT trust the user's category/tag names. If a requested category does not exist and they said "don't add new categories," pick the nearest existing parent or ask. Never invent taxonomy.
2. **Fact-check before publishing — and never outsource this to the bundle's own banner.** If the article makes factual claims (recall counts, casualties, statistics, quotes, dollar amounts, **which regulator issued an action**), verify against the primary source cited. If the draft contradicts its own source, do NOT publish the false claim — correct it and tell the user. A file titled `..._FULLY_VERIFIED.md` proves nothing; see "A bundle labelled FULLY VERIFIED is NOT fact-checked". Publishing inaccurate facts under the site byline is a real legal/editorial liability.
3. **Resolve term IDs by slug, not name search.** `GET /wp/v2/categories?slug=the-slug` is reliable; `?search=Name` is case/exact-match sensitive and can miss. Build a name→slug table from a supplied sitemap/category export.
4. **Fix links.** Replace dead internal URLs with live article URLs from the site's sitemap (if supplied). Verify external links return 200; fix 404s to the correct canonical URL (e.g. BLS CPI-E is `/cpi/research-series/r-cpi-e-home.htm`, not the chained-CPI page).
5. **DRY-RUN PARSE BEFORE PUBLISHING.** When ingesting a multi-article "package" text file, parse each article's fields (title, meta, categories, tags, focus, slug, body) and print them WITHOUT hitting the network, then eyeball that titles/slugs aren't polluted by trailing "Character Count" lines or backtick wrappers. Markdown `**bold**` and trailing `---` separators routinely leak into parsed fields if the regex is loose — fix the parser, re-dry-run, THEN publish. Also print the per-article **paragraph count** and confirm it matches the source (see Pitfalls: paragraph structure). (Template: `scripts/batch_publish.py` supports `DRY=1`.)
6. **Publish via POST** `status:"publish"` (or `"draft"` to stage). Body: `title`, `slug`, `content` (HTML with ONE `<p>` PER PARAGRAPH — see Pitfalls), `categories` (IDs), `tags` (IDs). Do NOT send Yoast `meta` in the POST — it is silently dropped by this host. Immediately after, **PUT** `/wp/v2/posts/<id>?context=edit` with `{"meta":{"_yoast_wpseo_metadesc":"...","_yoast_wpseo_focuskw":"..."}}` to set the SEO fields (the only method that persists — see gotchas). Pace with `time.sleep(3)` between every network write in a batch.

## CHECK FOR AN EXISTING POST ON THE SAME STORY BEFORE PUBLISHING (topic, not just slug)
The idempotent `?slug=` skip only catches a re-run of *your own* script. It does NOT catch the site already carrying that story under a different slug — and news sites routinely do, because the same wire story gets written twice.

2026-08-06: a 7-article package was published in full, and two of them duplicated posts already live:
- new `drug-resistant-salmonella-egg-recall-19-million-2026` vs existing `midwest-poultry-services-egg-recall-salmonella-2026` (2 weeks old)
- new `candida-auris-drug-resistant-fungus-hospital-outbreak-2026` vs existing `candida-auris-23-states-3000-cases-cdc-urgent-threat-2026` (published the day before)

Both slugs were unique, so every automated guard passed. The collision was only visible from a topic search.

**Rule: before a batch, run one `GET /wp/v2/posts?search=<distinctive noun>&per_page=5&_fields=id,slug,title,date` per article** using the story's most distinctive proper noun (`salmonella egg recall`, `Candida auris`, `Zoox`, `Fuego`) — the same posts-search you already run to harvest internal links, so it costs nothing extra.
- **The ENTIRE package may already be live.** 2026-08-06: all 9 articles were already published that day under different slugs with different bodies, so `?slug=` and body checks both passed — only TOPIC+DATE caught it, and the user did not know. Detect in the link-harvest pass (same-day post as hit #1), audit with `&status=publish,future,draft`, STOP before any write, and fact-check the LIVE version too — it beat the file on 4 of 9. `references/package-already-published.md`. Fold it into the internal-link harvest pass.
- **Surface the collision BEFORE publishing and let the user decide** (publish anyway / skip / update the existing post). Do not silently create the duplicate.
- If you have already published, say so plainly and offer to trash one — name both post IDs and dates so the choice is one reply. Do not bury it under the success table.
- A near-duplicate is also a *fact-check* signal: the older post may carry different numbers for the same event, and one of the two is wrong.

## Scheduled batch publishing with random gaps (future posts + resumable runs)
When the user wants posts released over time with a gap between each (e.g. "random 10–30 min gap"), publish them as **scheduled future posts**, not all at once:
1. Set `status:"future"` and a per-post `date` (ISO 8601, UTC) that increments by a random `timedelta(minutes=random.uniform(10,30))` from a near-future start (`datetime.now(timezone.utc) + timedelta(minutes=2)`). WordPress releases each once its clock hits — no manual `time.sleep` pacing needed.
2. **Make the run idempotent** so an interrupted run can be re-launched safely: before each POST, `GET /wp/v2/posts?slug=<slug>&per_page=1`; if it already exists, SKIP. This lets you re-run the same script after a crash without duplicating posts.
3. **Run in BACKGROUND** (`background:true, notify_on_complete:true`), never foreground. A 16-post batch with taxonomy discovery + tag creation + 16 publish POSTs routinely exceeds the 180s foreground cap and gets killed mid-run — the tail of posts then never publish. Background also frees you to keep working; poll with `process(wait)`.
4. **Caveat — `future` flips to `publish` once the time passes.** If a run is interrupted and you re-launch later, already-scheduled-but-now-past posts publish **immediately** on the re-run (their `date` is in the past), so the gap structure only holds within a single uninterrupted run. For a clean single sequence, schedule them all in one background run. Also: posts whose `date` is in the past at creation go `publish` instantly — confirm the start time is in the future.
5. **Author/category mapping from per-author buckets:** see the Author assignment section. Assign each story to the author whose beat fits (buckets are hints). Resolve category slugs to REAL site IDs — e.g. karmactive has **no `recall` category**; map weather/recall-bucket stories to `news` + `weather`.
6. **"Start N hours ago" — use `status:"publish"` + a BACKDATED `date_gmt`, not `status:"future"`.** When the user says "keep 10 to 30 min random gaps, start 2 hours ago," set the first `date_gmt` to `now - 2h` and increment by `timedelta(minutes=random.randint(10,30))`. Send `status:"publish"`; WordPress **auto-converts each post to `future` on its own** when the supplied `date_gmt` is still ahead of server time, and leaves the backdated ones genuinely published. The 2026-08-05 run produced exactly this split — the first 7 came back `status: publish` (timestamps already passed) and the last 7 `status: future` — from one uniform POST. You do NOT need to compute which side of "now" each post falls on.
   - **Check the server's clock, not the local one:** `curl -sI https://www.karmactive.com/ | grep -i '^date'`. The host may be hours off your machine, which changes how many posts go live immediately.
   - Backdated posts appear in the archive at their stated time, so a "2 hours ago" start makes the batch look like steady coverage rather than a bulk dump.

## Author assignment (multi-author / per-author-hint packages)

When the user hands you a batch where articles carry front-matter **categories** AND separately supplies **author→category beats** (e.g. "sunita: business, policy, social welfare"), treat the beats as HINTS for choosing the author — not as the post's categories.

- **Categories come from the article, not the bucket.** Map each article's OWN front-matter category names to the real site taxonomy (step 1 above). Do NOT force the article into the author-bucket categories.
- **Pick the author by subject-matter fit** to the article's actual topic, using the buckets only as a rough guide to each writer's beat. A product-recall story goes to the author whose beat includes "recall," not to whoever the bucket happened to list.
- Confirmed by user (out-of-band, this session): *"don't stick to categories mentioned with authors, these are just reference so you can assign the author … but choose the categories as mentioned in the articles … just select author as per their subject expertise in categories."*

**Resolving author IDs (slugs are NOT guessable):** the name the user gives (e.g. `sonali`, `rahul`, `karmactive team`) usually does NOT match the real WP user slug. Real examples on karmactive.com: `sunita`→`sunita-somvanshi` (57), `sonali`→`sonali-tiwary` (224), `rahul`→`rahul-somvanshi` (4), `govind`→`govind-tekale` (3), `karmactive-staff` (59), `karmactive team`→`admin` (1).
  - Fetch `/wp/v2/users?per_page=100` across **all** pages (karmactive has 324 users / 4 pages). The listing is prone to **transient 504** on Cloudflare — wrap in a retry loop (see gotchas).
  - Then grep the returned JSON by **name fragment** (`sunita`, `sonali`, `rahul`, `team`, `karmactive`), not by slug guess.
  - Cached ID table (verify before trusting — IDs can change): `references/author-ids.md`.

## REUSING an image already in the site's media library (no re-upload)
After any bulk upload, VERIFY post→media mapping live via `scripts/verify_featured_images.py`:
a drifted `(post,file)` loop silently assigns wrong heroes yet prints success (6/14 were
wrong in one batch). Also `vision_analyze` every sourced candidate — filenames lie.
Detail + examples in `references/featured-image-workflow.md`.
**Check this path FIRST, before sourcing or uploading anything.** A WP attachment can serve as `featured_media` on any number of posts, so when the user points at an image already on the site the correct move is to resolve its existing media ID and assign it. The user is explicit about this: *"DONT DOWNLOAD AND UPLOAD AGAIN, JUST USE THE SAME IMAGE ON KARMACTIVE."* Re-uploading a duplicate is a real error, not a harmless one — it litters the library with orphans you cannot DELETE via the app password.

1. **Resolve the URL to a media ID via `?slug=`, NOT `?search=`.** Derive the slug from the filename: drop the directory and extension, strip any WP size suffix (`-506x480`, `-720x480`, `-1024x682`), lowercase, and collapse every non-alphanumeric run to `-`. Worked examples from 2026-08-05:
   - `.../2026/08/RBI-Tower-506x480.webp` → `slug=rbi-tower` → media **271391**
   - `.../2025/05/FALCON-720x480.jpg` → `slug=falcon` → media **237459**
   - `.../2024/07/image-802-720x480.png` → `slug=image-802` → media **95468**
   - `.../2025/07/Paris-Bans-Cars-and-Closes-Schools-as-Heatwave-Hits-41%C2%B0C-1-720x480.jpg` → `slug=paris-bans-cars-and-closes-schools-as-heatwave-hits-41c-1` (the `°`/`%C2%B0` collapses to a bare `c`)
   ```bash
   curl -s --max-time 40 -A "$UA" -u "$AUTH" \
     "https://www.karmactive.com/wp-json/wp/v2/media?slug=rbi-tower&_fields=id,source_url,alt_text"
   ```
2. **`GET /wp/v2/media?search=<term>` HANGS on this site — never use it.** It burned a 180s AND a 500s foreground timeout with zero output on queries that `?slug=` answers in ~1.9s; the library is large enough that `search` scans pathologically. If you have only a keyword and no filename, come at it from the posts side instead (posts search is fast): `GET /wp/v2/posts?search=<term>&per_page=4&_fields=id,title,featured_media`, then `GET /wp/v2/media/<featured_media>?_fields=id,source_url,alt_text` to inspect each hit. That **posts → featured_media → media** hop is also the best way to mine the existing library for a reusable image on a given topic, and it returns the alt text already written for it.
3. **If the user supplies an ARTICLE url where you expected an image url,** fetch that post, read its `featured_media`, and reuse that same id — then tell the user that's how you read it. (2026-08-05: the LPG post was given as an article link; its own hero, media 270987, was the intended image.)
4. Assign exactly as for a fresh upload: `POST /wp/v2/posts/<id>` `{"featured_media": <existing_id>}`. **Do not rewrite the reused media's alt/caption/title** unless asked — other posts share that attachment and a caption rewrite changes the hero caption everywhere it appears.
5. Reuse still needs the **two-layer verification** below (DB + rendered hero).

### Mining the library for a WHOLE BATCH (topic sweep, not a named file)
When the user says "first find what images can fit for these articles from pre-uploaded photos on karmactive and just show me," run a scripted `posts?search=` sweep — 2–3 topic terms per article, dedupe by `featured_media`, then `GET media/<id>` for `source_url` + `alt_text`. Budget ~8–10 min in BACKGROUND for 14 articles × 3 terms; it exceeds the foreground cap.

**Calibrate expectations: WP `search` matches ARTICLE TEXT, not image content — most hits are noise.** Two sweeps ran ~120 candidates → 3 usable, and 60 → 2. Everything else was category-adjacent but wrong: a **dusky** shark for a **tiger** shark article, an **Indian Punjab** wheat tractor for a **British** harvest, an **Indian Railways** interior for a **UK** commuter line, **blueberries** for a frozen-spaghetti recall, a Cybertruck for "battery storage." The 3 genuine hits were a `chips` photo for a Lay's recall, `College-graduation.jpg` for a student-loan story, and `surgeon-operating-theatre.webp` (empty theatre, so no clinician wrongly implicated) for Candida auris.

**VISION-VERIFY REUSED SITE MEDIA TOO — the karmactive filename lies just as often as a Commons title.** The vision-verify rule in the Commons section (sourcing step 7) applies with equal force to images already on the site. 2026-08-05: media 268873's filename `Dusky-Sharks-Kill-Snorkeler-...jpg` and its stored alt text both said dusky shark, so the agent wrote a caption disclaimer *"(Representative image — dusky shark, not the tiger shark described)"* for a **tiger** shark article. `vision_analyze` showed a **tiger** shark — blunt squared snout, faint flank bars. Filename and alt text were both wrong, and the error had been propagated into a published-facing disclaimer.
- **Rule: before writing any species / country / model / institution claim into a caption — including a `(Representative image)` disclaimer — `vision_analyze` the actual pixels.** A wrong disclaimer is its own error: it tells readers the photo is a stand-in when it is in fact the real subject.
- Stored `alt_text` on existing media inherits whatever the original uploader wrote. Treat it as a hint, never as verification.
- **Do not judge an image from the wp-admin list thumbnail or a small preview.** Same session, `College-graduation.jpg` read as "a textured brown/black surface" at admin-list scale; the full-size file is unambiguously a graduation crowd. Always inspect the full-size `source_url` before rejecting a candidate.

**Apply the SUBJECT-RELEVANCE RULE to reuse candidates exactly as strictly as to Commons hits** — wrong species / wrong country is precisely the "COMPLETELY WRONG FOR THE ARTICLE" failure. Present borderline ones in the table but recommend sourcing instead, and say why in one clause ("dusky, not tiger"). Report the split plainly: *"3 reuse, 11 to source."* Do not pad the reuse column to look thorough.

**Also run the batch HAS/EMPTY audit in parallel** — a fresh batch is often `WITH IMAGE: 0 | STILL EMPTY: 14`, which reframes the whole job as "every post needs a hero," not "fill the gaps."

**SHOW the candidates as embedded images — a filename table is not "showing," and neither is a local file path.** After the sweep, render each shortlisted candidate inline: `![](source_url)` for site media, `MEDIA:<absolute path>` for local files. On 2026-08-05 a media-id/filename/alt table drew *"CAN I SEE?"*, and a list of newly-downloaded Commons files by name/size/license drew *"WHERE ARE THE IMAGES"* — the same complaint twice in one session. **Every image hand-off must be visual, whatever the provenance.** Group them **STRONG** vs **BORDERLINE** (name the defect in one clause: "dusky, not tiger"; "Punjab, India — not Britain"), and list articles with no candidate underneath. The user then approves in one pass ("5,9,13,11 ARE OK USE THEM").

**On approval, assign by id only** (`POST /posts/<id> {"featured_media": <id>}`) and **do not rewrite the reused media's caption/alt/title** — those attachments are shared with the posts they came from. Write the caption/alt/title text out in chat for the user instead, and say why you didn't push it.

## Featured image assignment (media + featured_media)
Use this to backfill or set thumbnail images on already-published posts.
1. **Find candidate posts by title keyword:** `GET /wp/v2/posts?search=<term>&per_page=5&_fields=id,title,link,featured_media,date`. Only assign where `featured_media: 0` (image missing) — never clobber an existing one unless told to.
2. **Upload the image:** `POST /wp/v2/media` with multipart `-F "file=@<path>;type=image/webp"`. The response JSON carries `"id"` — that's your media id. (WebP uploads fine; server creates sized variants.)
3. **Set alt text + caption + title on the media item** (accessibility + SEO + the user's required caption/title spec): `POST /wp/v2/media/<id>` with `-H "Content-Type: application/json"` and body `{"alt_text":"<desc>","caption":"<Caption per spec>","title":"<short noun phrase>"}`. All three persist on the media item in one call (the article's hero then shows the caption). The caption/alt/title values come from the user's caption spec (see Caption / alt text / title spec); strip any HTML from source attribution first (see free-image-sourcing step 1).
4. **Assign to the post:** `POST /wp/v2/posts/<id>` with `{"featured_media":<media_id>}`. Unlike Yoast meta (which needs `PUT` + `?context=edit`), featured_media assignment works via **POST and persists immediately**.
5. **Verify TWO layers, not one — the rendered page is the real proof.** Step A (DB): `GET /wp/v2/posts/<id>?_fields=link,title,featured_media` and confirm `featured_media` equals the uploaded media id. Step B (RENDERED PAGE — this is the layer that catches overrides): `curl` the public `/slug/` and `grep` for the hero `<img>` (`fetchpriority="high"` src, or `wp-post-image` / `fifu-featured` class). If the rendered `src` differs from the file you uploaded, a theme/plugin/cache is overriding your assignment. A site with the **FIFU ("Featured Image From URL") plugin active** will report `featured_media` correct in Step A yet serve a COMPLETELY DIFFERENT image in Step B (e.g. a bus for a subway article, a foreign police car for a local story). See the FIFU gotcha in "Verified gotchas" and the diagnostic recipe `references/fifu-featured-image-override.md`.
- Runnable bash loop + JSON-safe alt-text helper: `references/featured-images.md`.
- Matching rule of thumb: match a local image filename to a post by a distinctive token in the filename (e.g. `RBI-Tower.webp` → post titled "RBI New Deposit Rules"; `typhoon_1920x1080*.webp` → "Super Typhoon Dolphin"). Hold off on ambiguous files rather than guess-match to the wrong article.

## Sourcing free / zero-copyright images (when the user has none locally)
For "find images for articles with no featured image" jobs, pull from **Wikimedia Commons** (cleanest license metadata via API). Do NOT use random Google images (copyright landmines).
1. **Search + filter by license in one API call:** `action=query&generator=search&gsrnamespace=6&gsrsearch=<term>&prop=imageinfo&iiprop=url|size|mime|extmetadata|mediatype&iiurlwidth=1280`.
   - **JSON parse pitfall (Commons API):** raw API responses contain literal control characters (e.g. `\x00`, tab) embedded in metadata fields that make `json.loads()` throw `JSONDecodeError: Invalid control character` / `Expecting ',' delimiter`. The reliable fix is to **write the response to a file and parse the file**, stripping control chars first: `re.sub(r"[\x00-\x1f]","",raw)` then `json.loads(cleaned, strict=False)`. Do NOT pipe the curl output straight into an inline `python -c` JSON parse — the captured stdout gets mangled. Also **avoid `extmetadata` detail you don't need** (description fields bloat the payload with the offending control chars); `url|mime|extmetadata` with `LicenseShortName`/`Artist`/`License` is enough.
   - **Strip HTML from attribution before using it.** The `Artist` and `Credit` fields returned by the Commons `extmetadata` are often HTML-wrapped (e.g. `Artist` comes back as `<a href="...">SuperJet International</a>` and `Credit` as `<a href="...">Flickr: Loïc Le Meur on Google Glass</a>`). If you copy them verbatim into a WP caption/alt/title you'll inject `<a>` tags into the published caption. **Fix:** `re.sub(r"<[^>]+>","",artist).strip()` (and same for credit) right after parsing, before writing the caption. The 2026-08-05 batch did this and produced clean `[Photo: SuperJet International / Wikimedia Commons, CC BY-SA 2.0]` brackets with no leaked markup. (Bengali/non-Latin author names like `পাপৰি বৰা` come through as plain text and are preserved as-is — no stripping needed, just no Latin transliteration invented.)
2. **License allowlist (news-safe):** accept only `CC0`, `CC BY`, `CC BY-SA`, `Public Domain`, `PD-*`, `NASA`, `NOAA`. **Reject** anything with `NonCommercial`/`NC`, `NoDerivatives`/`ND`, `Copyright`/`All Rights Reserved`/`Restricted`/`Trademark` — unsafe for commercial/news reuse.
3. **Prefer horizontal, decent-width** bitmaps (`mediatype=BITMAP`, mime in jpeg/png/webp/tiff); skip SVGs/PDFs.
4. **Download the `thumburl` (1280px), not the original.**
5. **Compress to webp <100 KB locally with Pillow.** Browser-only "online" converters (giganectar.com and similar) process entirely in-browser and CANNOT be driven from the REST/terminal layer — local PIL is the only path and gives an identical result: `img.convert('RGB'); img.thumbnail((1600,1600)); buf=io.BytesIO(); img.save(buf,'WEBP',quality=q,method=4)` — loop quality 82→35 until `buf.tell() <= 100*1024`. Cap longest side at 1600px first. (If a user pastes such a converter URL, explain it's client-side-only and use Pillow instead — do NOT attempt to POST images to it.)
   - **If the quality loop plateaus ABOVE 100 KB on a dense photo, also reduce the longest side.** A 1200px image can stick at ~111 KB even at the q=26 floor. Drop width (1200→1100→1040) and re-loop; target ≤98 KB for margin. (Confirmed: the CJP/Jantar Mantar image needed width 1040 + q≈35 to land at 93.9 KB; quality-only loops at 1200px never got there.)
5. **Relevance flag for the journalist:** Commons rarely has a photo of the *specific 2026 event*; you'll often get a generic/illustrative stand-in (e.g. a 2019 hurricane for a 2026 storm, an 1887 farmer for a modern scheme, a Beijing subway for an NYC flood). List each as "license-clean but TOPICAL APPROXIMATION" and let the user swap before you upload. Runnable recipe: `references/free-image-sourcing.md`.

6. **SUBJECT-RELEVANCE RULE (hard, learned from a user correction):** the image must depict the article's *specific subject*, not just its category. A stock-exchange trading floor is right for a hedge-fund collapse; a generic **data-center server room is NOT** (off-topic). A **modern Indian farmer in a field is right for PM-Kisan; an 1887 US Hopi farmer photo is NOT** (wrong country/era). A **pharmacist at work is right for a pharmacist result; a PICUP government building is NOT** (different subject). When sourcing, read the article excerpt first and pick a file whose subject literally matches the headline noun (exchange, farmer, pharmacist, subway, wildfire, vaccine…). The user will reject category-only matches as "COMPLETELY WRONG FOR THE ARTICLE" — so never fall back to a loosely-related stand-in without flagging it as a TOPICAL APPROXIMATION for their review first (see step 5). If the only Commons result is a weak match, say so and hold, rather than upload a wrong-subject image.
- **Institution / scheme / government-body articles:** the body's OWN building, HQ facade, logo, or official emblem is the strongest subject match — stronger than a generic demographic stock photo of the people it serves. This session: for the EPFO (pension scheme) article the right call was the **EPFO Head Office facade** (signage reads "Employees' Provident Fund Organisation"), NOT a generic "group of senior citizens" photo — the building IS the subject, the retirees are only the beneficiaries. Same logic for a ministry / RBI / bank article → its headquarters, not a crowd of customers.

7. **VISION-VERIFY every Commons candidate before presenting it — the filename and your search term both lie.** Commons titles are user-supplied and frequently wrong, and the search engine returns near-misses that read as exact matches in a text listing. `vision_analyze` each downloaded file and describe what it ACTUALLY depicts, then report the mismatch to the user rather than letting them discover it on the live site. Three real misses caught this way on 2026-08-05, all of which would have shipped silently:
   - Searched `swimming breaststroke` → the top CC-BY-SA hit is a **freestyle** stroke by a **female Australian** swimmer; the article subject was a **male Scottish breaststroker**. Stroke, sex and nationality all wrong.
   - Searched `surgeons operating theatre` → the image is an **empty** theatre. (For a medical-negligence story that is arguably better — no identifiable clinician wrongly associated with misconduct — so report the nuance, don't just reject.)
   - A file titled `C1 building of Sinhgad College of Engineering, Pune.jpg` has signage that actually reads **"M.G. College of Engineering"** — not the institution the filename claims.
   State each mismatch plainly in the hand-off ("license-clean but TOPICAL APPROXIMATION, and here is specifically what's off"). The user would rather swap an image at review time than find a wrong one published.

8. **Search the SPECIFIC place/institution/exam name, not the generic category noun.** This user routinely out-picks generic Commons searches by naming the actual subject, and their picks are better because the query was more specific — copy the technique rather than waiting to be corrected. On 2026-08-05 they overrode two of the agent's choices mid-run:
   - LPG-autogas-in-**Bikaner** article: agent searched `commercial LPG cylinders` → red gas cylinders (category-correct, place-blind). User supplied `File:Bikaner-Junagarh-20-Guru steigt in Tuktuk-2018-gje.jpg` — an **auto-rickshaw outside Junagarh Fort in Bikaner itself**. Needed no `(Representative image)` tag at all, because it genuinely depicts the subject.
   - NEET-UG-counselling article: agent searched `exam` → generic students-in-a-hall. User supplied `File:AIPMT-2011 - Kolkata 2011-04-03 00192.jpg` — candidates crowding an **actual all-India pre-medical entrance exam** centre gate.
   **Rule:** before searching, extract the proper nouns from the headline — city, fort/landmark, institution, exam acronym, agency — and query those FIRST (`Bikaner autorickshaw`, `AIPMT examination`, `Junagarh Fort`). Fall back to the generic category noun only when the specific query returns nothing license-clean. A place-specific hit removes the "representative image" caveat entirely, which is strictly better for a news site.
   - **Fetching a user-named Commons file by exact title:** `action=query&titles=File:<exact title>&prop=imageinfo&iiprop=url|size|extmetadata&iiurlwidth=1600` (use `titles=`, not the search generator). Same control-character parse guard applies. Then vision-verify, compress, upload, assign — and if it supersedes an image you already assigned, just reassign `featured_media` to the new id and abandon the old one (DELETE returns 404, see gotchas).

## Sourcing images the user points to on Facebook / social media (login-gated, non-licensed)

   ```js
   JSON.stringify(Array.from(document.querySelectorAll('img'))
     .map(i=>({s:i.src,w:i.naturalWidth,h:i.naturalHeight}))
     .filter(x=>x.w>200))

The signed `fbcdn` URL carries an `oe=` expiry, so download promptly if you intend to use it.
   If the DOM read fails, fall back to asking the user to **download the image file** (right-click → "Save image as", NOT a screenshot of the post) into `Downloads/feature images\`.
1b. **Being able to fetch it does not mean you should publish it — check SUBJECT and LICENSE before offering it.** A Facebook photo from a company's own page is a copyrighted corporate marketing asset, and usually shows *brand*, not *subject*. 2026-08-05: the user said "USE THIS FOR OCTOPUS" for an Octopus Energy Facebook photo; the pixels were an **Octopus-branded London taxi with two identifiable staff in company polo shirts** — for an article about a 98.5 MW grid battery in Sessa Aurunca, Italy. ## User-supplied LOCAL image files with no license metadata
Sometimes the user points you at a local file they already have on disk (e.g. an org's HQ photo, a press-image webp, a screenshot) rather than a Facebook URL. Handle like the social-media case but adapt:

## Caption / alt text / title spec (this user's standard — apply verbatim unless overridden)
The user issued this spec twice, word-for-word; treat it as a hard default for any featured-image caption work.

## Scheduling a batch in TWO runs collapses the gap structure — plan all N up front
When a package turns out to be short some articles (see "Count `### CONTENT` sections") and you publish the found ones first, then add the missing ones in a second script, the second run's `date_gmt` sequence is computed **independently** of the first and the two interleave with sub-minute collisions. 2026-08-05: run 1 scheduled 11 posts on a clean 12–27 min ladder; run 2 added 3 more starting `now+12min`, landing Apophis **3 min** after Tiger Shark and Baylen **1 min** after Danube — visibly violating the user's stated 10–30 min rule, and they spotted it in the wp-admin list.
- **Fix:** before the second run, GET the existing batch's `date_gmt` values, take the max, and start the new sequence from `max + randint(10,30)` minutes. Never start a continuation run from `now`.
- **Better:** resolve the missing-article question BEFORE any publishing (structural grep first), so all N go out in one uninterrupted run.
- Report the collision honestly if it happens; offer to re-space the affected timestamps rather than hoping it goes unnoticed.

## Commons search misses are common — re-query with place names before settling
A generator search returning **0 results** or obvious junk is a query problem, not a "Commons has nothing" verdict. Same session, `Prahovo shipwrecks Danube` and `Danube low water drought` returned 0, while a bare **`Prahovo`** returned 10 license-clean files. Likewise `battery storage Japan` returned a Nintendo Switch teardown — but `KAZENOMATSUBARA Co. storage battery facility` was in that same result set and was the right answer.
- **Rule: when a multi-word event query returns 0, drop back to the bare place name / institution name alone.** Commons is indexed on what the photo *is*, not the news event it might illustrate.
- Commons will essentially never hold a photo of a *specific recent event*. Expect to source the **location** or **object class** and tag it `(Representative image)`.
- **Place-name hits still need vision-verification**, and budget a ~20% reject rate — re-source immediately rather than handing over a broken row. Confirmed misses: a "Prahovo Port" file that is a railway yard with a blue passenger train; a `Fire engine on Saltmarket` that is a 1990s Scania at a Glasgow parade. Both replacements were found in one more query round; save replacements with a `-ALT` suffix.
- **Vintage / parade / museum vehicles are a recurring trap for emergency-services stories.** Query the *incident* (`firefighters hose building fire`, `fire damaged building`), not the vehicle, and confirm active smoke/water + modern kit in the vision check.
- **A cross-river/cross-country substitute still needs the `(Representative image)` tag** and must credit the real location — never imply it is the article's river.
- **Commons fetch mechanics that look like blocks but aren't** — `1400px` thumbnails return a 2009-byte HTML error page (use **1280px**; tell-tale is every file downloading at an identical byte count), `upload.wikimedia.org` 429s `vision_analyze` (download first, verify the local path), a vision-tool 404 on a `.webp` does NOT mean the file is missing (curl + `Image.open` first), searches need `filetype:bitmap` + an extension/width filter or they return PDFs, and **diacritics zero out a query** (`Volcán de Fuego` → 0 hits; `Fuego volcano` → 8). ## Verified gotchas (karmactive.com — Cloudflare-protected WP)
- **Always use the www host.** Bare domain 301-redirects; API only answers on `https://www.karmactive.com`.
- **WAF blocks non-browser User-Agents.** Cloudflare returns `403 error code: 1010` on REST calls with curl/urllib default UA; auth may pass on GET but POST is blocked. **Fix:** send `User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0 Safari/537.36` on EVERY request.
- **Yoast SEO meta DOES persist — but ONLY via PUT + `?context=edit`.** A `POST` (even with `?context=edit`) silently drops ALL meta writes, including a throwaway custom key — looks like a server-side block on POSTed meta. The working method: `PUT /wp-json/wp/v2/posts/<id>?context=edit` with body `{"meta":{"_yoast_wpseo_metadesc":"...","_yoast_wpseo_focuskw":"..."}}`. Read-back confirms it; the live `<head>` then emits `<meta name="description">`. (A prior version of this skill wrongly claimed meta never persists — that was the POST bug, not a real limitation.)
  - Keys use the leading-underscore DB form (`_yoast_wpseo_metadesc`, `_yoast_wpseo_focuskw`, `_yoast_wpseo_title`). Without-underscore, `yoast_seo` top-level, and `custom_fields` top-level do NOT work. XML-RPC is fully blocked (Access Denied page), so PUT is the only path.
  - After a PUT, the public page may still show OLD meta due to **FastCGI page cache** (`X-FastCGI-Cache: HIT`). Verify with `?nocache=1` (cache MISS) — meta then appears. The cache self-expires; purging needs wp-admin or a Cloudflare token (not available via app password, so just wait it out or re-save the post in the editor).
- **User role is `author`** — can edit own posts (those published under user 224 / Sonali Tiwary). PUT meta on those works fine.
- **Resolving author IDs when slugs don't match:** the author name the user gives is usually a *fragment*, not the real WP slug (e.g. `sonali`→`sonali-tiwary`, `rahul`→`rahul-somvanshi`, `karmactive team`→`admin` id 1). Paginate `/wp/v2/users?per_page=100` (karmactive has 324 users / 4 pages) and grep the returned JSON by **name fragment**, not by slug guess. Fetch WITHOUT `context=edit` for the ID table.
- **504 on the users listing is transient, not a block.** Cloudflare returns 504 (gateway timeout) on the `/wp/v2/users` listing even when single POSTs succeed. Distinguish it from 401/403: 504 → retry-loop the listing; 401/403 → fix the www host + browser UA (see top of gotchas). A `?context=edit` on the users list can *itself* trigger 504.
- **FIFU plugin overrides `featured_media` (rendered hero ≠ DB assignment).** Symptom: you upload + set `featured_media` correctly, `GET /wp/v2/posts/<id>` returns the right id, but the public page hero shows a DIFFERENT image (often a pre-existing "representative" image). Root cause: the **"Featured Image From URL" (FIFU) plugin** is active and the theme renders the hero from FIFU fields (`_fifu_image_url`, `fifu-featured` markup in HTML), not the native `featured_media`. The app-password REST context **cannot write FIFU meta** — `POST`/`PUT` with `{"meta":{"_fifu_image_url":...}}` or `{"meta":{"_thumbnail_id":...}}` is silently filtered and read-back shows `None`. So your assignment is correct in the DB — and for the COMMON case (a post with no prior featured image) it renders correctly: the article hero `wp-post-image` `<img>` serves your uploaded file. FIFU only overrides the rendered hero when the post ALREADY carries a `_fifu_image_url`; then the page shows a DIFFERENT image. **Distinguish before alarm:** after assigning, curl the public page and check the FIRST `wp-post-image` img src/data-src — if it is your uploaded file, you are done. Only if it shows a DIFFERENT image is FIFU overriding. If so, **Fix path (needs wp-admin, NOT the REST API):** open each post in the editor, set the native **Featured Image** to the correct uploaded file (writes `_thumbnail_id` properly) AND clear/empty the FIFU URL box; then clear any page cache / CDN. If the user supplies wp-admin login, drive the editor via the browser tool. Diagnostic + verification recipe: `references/fifu-featured-image-override.md`.
 - **Two distinct render layers.** The post page's true `wp-post-image` `<img>` is driven by the native `featured_media` (which the REST API DOES set correctly), so the single article view often shows the RIGHT image even while a *feed/listing/card* view still shows FIFU's stale thumbnail (`fifu-featured="1"` `<img>` tags with the wrong `src`). Verify BOTH: the post `wp-post-image` AND any feed/archive where the article appears. Clearing FIFU's URL + purging cache fixes the feed layer.
 - **Deleting old/wrong media via REST does NOT work with the app password:** `DELETE /wp/v2/media/<id>` returns `HTTP 404` (the app-password context lacks the capability), so you cannot clean up superseded images through the API — they linger in the media library and must be trashed in wp-admin. Just leave the old media in place (or flag it for wp-admin cleanup); assign the NEW media id to the post instead.
  - **Consequence — when re-doing a featured image, upload-fresh-and-reassign rather than update-in-place.** To avoid piling up orphaned media, prefer uploading a NEW image and reassigning `featured_media` to the new id, then leave the old one unreferenced. Attempting `DELETE` to tidy up returns 404 and burns a call. This session: swapping the CJP post's irrelevant featured image meant uploading 3 sizes (115 KB → 111 KB → 93.9 KB) and reassigning each time; `DELETE` on 271529/271530/271531 all returned 404 — only `assign-new-id + abandon-old` was viable. The compress-under-100KB loop should therefore target a fresh file each time (or accept one orphan).
- **Shell helper (MSYS/Windows):** `python3` may be absent (use `python`); `/tmp` may not exist. Write the `.py` helper to the working dir and run `python script.py`. See `scripts/publish_post.py`.
- **`GET /wp/v2/media?search=` is pathologically slow on a large library — use `?slug=` instead.** On karmactive 2026-08-05 a 7-term media `search` loop burned a 180s AND a 500s foreground timeout with zero output, while the equivalent `?slug=` lookups answered in ~1.9s each. The posts endpoint's `search` is fine; only **media** `search` hangs. If you have a filename → derive the slug (see the media-reuse section). If you have only a keyword → go `posts?search=` → read `featured_media` → `GET media/<id>`. Never leave a bare media `search` in a batch loop; one hang kills the whole run and you lose every result before it.

## SPLIT the publish pipeline into SMALL modules — one giant script write times out
A single `write_file` carrying the whole pipeline (REST helpers + article table + corrections + link table + build + publish) exceeds the ~8K-token tool-argument limit; the stream times out before the call is even delivered, and retrying the same payload fails identically. 2026-08-06 (11-story karmactive batch) only moved after splitting into small files, each written or `patch`-ed independently:
- `kx_lib.py` — curl/REST `api()` helper, package-file parser, `md2html`, wordcount/readtime
- `kx_art1.py` / `kx_art2.py` — the `ART` metadata dicts, ~6 articles each (a `CAT = dict(...)` of live category IDs lives in art1 and is imported by art2)
- `kx_links.py` — the anchor→URL table
- `kx_fix.py` — fact-check body corrections
- `kx_build.py` — assembly + `DRY=1` dry run
- `kx_publish.py` (network writes) and `kx_audit.py` (field audit)

**Never retype article bodies into the script.** Parse them from the source `.md` on disk — `re.split(r"^# STORY (\d+):", txt, flags=re.M)`, then slice between the body heading and the metadata heading. Retyping bodies is exactly what makes the file too large, and it silently introduces transcription drift. Iterate with `patch` on the small modules, not by rewriting them.

### Apply fact-check rewrites as a keyed table, hard-failing on a miss
Keep corrections out of the article table and out of the body text, in their own module:
```python
DROP_LINES = {"9": ["Puget Sound Clean Air Agency", "Willamette Valley"]}   # substring match
REPLACE    = {"2": [(old_line, new_line), ...]}                            # exact-then-prefix match
```
In the build loop, `raise SystemExit("FIX MISS art %s")` when a correction no longer matches. Without that guard a correction silently no-ops and you publish the false claim while reporting it fixed. 2026-08-06 this table carried five substantive corrections (see the fact-check case below) and every one was proven applied by the dry run.

## Injecting links on anchor text (assert every anchor MATCHES before publishing)
When the job is "add external + internal links on appropriate anchor text," do NOT hand-write `<a>` tags into prose. Declare per-article `links = [(anchor_phrase, url), ...]`, then `html.replace(phrase, '<a href="…" target="_blank" rel="noopener">'+phrase+'</a>', 1)` and **count how many actually matched**.
- **The source body ALREADY has markdown links — a naive `phrase in md` check both false-negatives and nests links.** A package body typically ships 2–9 `[text](url)` links of its own. Use **candidate anchor lists** and match against a link-masked copy of the text:
  ```python
  LINK = re.compile(r"\[[^\]]*\]\([^)]*\)")
  for cands, url in LINKS[n]:                       # cands = ["long specific phrase", "short fallback"]
      for phrase in cands:
          if "[%s](" % phrase in md: placed = True; break        # already linked with this exact anchor
          plain = LINK.sub(lambda m: "\x00" * len(m.group(0)), md)  # mask existing links, preserve offsets
          i = plain.find(phrase)
          if i >= 0:
              md = md[:i] + "[%s](%s)" % (phrase, url) + md[i+len(phrase):]
              placed = True; break
      if not placed and any(p in md for p in cands): placed = True   # phrase sits inside an existing anchor
      if not placed: raise SystemExit("ANCHOR MISS art %s: %r" % (n, cands))
  ```
  The `\x00`-padding mask is the key trick: it keeps character offsets identical so the index found in `plain` splices correctly into `md`.
- **Verify anchor candidates against the plain text BEFORE building.** A throwaway 10-line script that masks existing links and prints `OK`/`MISS` per candidate turns a slow one-miss-per-run debug loop into a single pass. 2026-08-06 the first anchor table scored 4/44 — every hand-guessed phrase was invented rather than lifted from the body. Read the actual masked text, then copy real spans out of it.
- **Assert `used == len(links)` in the DRY-RUN and fail loudly** (`assert ... , "FIELD PROBLEM"`). A phrase that doesn't match silently ships an article with fewer links than intended while you report the full count. This session the assert fired on article 11 and caught a real 3/4 miss before anything was published — it is the single highest-value guard in the pipeline.
- **The #1 cause of a non-match is smart-quote vs straight-quote.** Source markdown carries curly `“ ” ’`; a hand-typed anchor in your script uses straight `" '`. **Rule: choose anchor spans containing only plain alphanumerics, spaces, commas and hyphens.** Keep quotes, em-dashes (`—`), and currency symbols (`£`, `₹`) OUTSIDE the anchor span — anchor on the words immediately around them instead.
- **Internal links must be REAL live URLs.** Harvest them first, one query per article topic: `GET /wp/v2/posts?search=<topic>&per_page=3&_fields=link,title`. Batch these in a single shell loop with `sleep 1` before writing the script. Never fabricate a site URL.
- Aim for ~4–6 links per article (a mix of external primary sources and internal karmactive posts); the audit should assert `content` has at least 3 `href=`.

## "Package" bundles with truncated bodies (`[Content continues with same linking pattern...]`)
A multi-stage delivery file (e.g. `STAGE4_5_COMPLETE_DELIVERY.md`) frequently gives, for most articles, only the first 2–3 fully-linked paragraphs followed by a literal `[Content continues with same linking pattern...]` marker plus a `**Key Links Embedded:**` URL list. Publishing that body verbatim ships a truncated stub.
**Correct handling:** take the **full body from the individual numbered source file** (`04_mht_cet_cap_results.md`), take the **SEO metadata from the bundle** (title options, meta, focus keyphrase, slug, tags), and re-apply the bundle's `Key Links Embedded` URLs yourself onto chosen anchor phrases in the full text. Then **tell the user the bundle was incomplete and what you did** — they need to know. (2026-08-05: 8 of 14 articles in the bundle were placeholder-truncated; all 14 published full-length from the numbered files.)

## A bundle labelled "FULLY VERIFIED / FACT-CHECKED" is NOT fact-checked

Treat the package file's own verification banner as marketing copy, not evidence. The 2026-08-05 `FINAL_STAGE_4_5_ALL_14_ARTICLES_FULLY_VERIFIED.md` opened with "THOROUGHLY VERIFIED — ALL CLAIMS CROSS-REFERENCED / Overall Accuracy 98.2%" and was still wrong.

1. **Mine the file's OWN status table for self-contradictions first — free leads.** That file's top table said `⚠️ ARTICLE 11: NEEDS VERIFICATION (metal contamination claim)` while its bottom summary said `✅ ARTICLE 11: VERIFIED`. When a bundle disagrees with itself, the pessimistic entry is the true one. Check that article before anything else.
2. **What the check found (the failure shape to internalise):** one `web_search` + one `web_extract` of the primary notice showed the draft had the **wrong agency** (said FDA; it was **USDA FSIS**, because meat/poultry recalls are FSIS not FDA), the **wrong geography** ("nationwide" vs NC/VA/WV + DoD + online), **no product identification at all** (vs Baked Spaghetti & Chicken Cobbler, 4 SKUs, EST. 19979 / P-19979, best-by 07/08/26–08/05/26), and **no quantity or cause** (vs 22,880 lbs, aluminum slivers off the baking pans, surfaced by a single consumer complaint). **Rule: any recall article naming a regulator must have the regulator verified. FDA vs FSIS vs CPSC is the most common error in these bundles.**
3. **The fix is a full body rewrite, not a patch.** Replace `bodies["<n>"]` wholesale from the primary source and update `title` + `slug` + `meta` to match (a slug promising `class-1-fda-alert` is wrong once you learn it's FSIS). Then re-run the dry run.
4. **Smell test for unsourced filler:** an article with no named docket/case number, no dollar figure, no quantity, no dates and no proper nouns beyond the company is almost certainly padding. Same batch: the Student Loan Settlement article named *no* settlement, docket, or amount — flag those to the user as thin even when you can't re-source them all.
5. **Report verification coverage honestly in the hand-off.** State explicitly which articles you independently checked against primary sources and which you published on the bundle's own claim. Do NOT let "published successfully" imply "fact-checked" — the user asked for fact-checked articles. Offer the re-check pass on the remainder; scheduled (`future`) posts are still cheap to correct or pull.

### The failure shapes to hunt for — full catalogue in `references/bundle-fact-check-failures.md`
Eight confirmed shapes with worked examples live in that file. **Read it before
fact-checking any bundle.** Shapes 5–7 need no network call, so run them first:
- **5. The article contradicts itself two sentences apart.** Superlatives
  ("record", "highest ever") are the highest-yield check — the draft usually
  supplies the refuting number itself. "Unlike X, Y does Z" is a reliable error
  site.
- **6. An incident date standing in for its disclosure date.** Event + response
  ("brought to Congress", "prompted the investigation") = two different dates
  until proven otherwise.
- **7. A hyperlink pointing at the wrong agency's page.** Check each URL's
  DOMAIN against the organisation named in its anchor text — cross-article link
  transplants are invisible to a span-match-only pre-flight.

Then spend searches on: **1.** a legal holding inverted (courts rule on legality
while punting on remedy); **2.** a fabricated citation URL on the *right* domain
(spot-check the docket number, not the host); **3.** body content cross-
contaminated between two same-theme articles in the bundle; **4.** a precise-
sounding number with no source; **8.** the wrong regulator (FDA vs USDA FSIS vs
CPSC — meat and poultry are FSIS).

**Also state what you did NOT verify.** Same session, market-sizing claims (a $100B obesity-drug market by 2030, 42% adult obesity, $170B annual cost) were left in place uncited and flagged to the user as unverified, with an offer to re-source. That is the honest shape of the hand-off: corrections listed with what changed and why, then an explicit residual-risk line.

## Count `### CONTENT` sections — a "14 article" bundle often carries fewer bodies
Summary tables can list every article while the body sections for some were dropped in a later revision. The 2026-08-05 `FINAL_..._ALL_14_ARTICLES_FULLY_VERIFIED.md` advertised 14 and had CONTENT for **11** (articles 2, 3, 4 existed only as ✅ rows). **Always** open with a structural grep before writing any publish script:
```bash
grep -n "^## ARTICLE\|^### CONTENT\|^\*\*Word Count" package.md
```
If the counts disagree, tell the user which numbers are missing and ask whether to publish the subset — do NOT silently publish a short batch, and do NOT backfill from a previous doc when the user said "DON'T PUBLISH ANYTHING FROM THE PREVIOUS DOC" (they had reason: the older version carried uncorrected facts).

## Thin-link articles: declare an EXTRA anchor table, don't lower the bar
The `assert used == len(links)` guard is for anchors that fail to match; the sibling failure is an article whose source markdown simply *has* too few links. The 2026-08-05 dry run flagged three at 1–2 links (Shropshire Zoo, UK Harvest, Student Loans). Add links, don't relax the threshold:
1. Soft-gate in the dry run (`if a["nlinks"] < 3: print("FEW LINKS"); ok=False` → `assert ok`) so thin articles surface *before* any network write.
2. Add an `EXTRA = {"<article-n>": [(anchor_phrase, url), ...]}` table applied to the **markdown** before `md2html`, wrapping as `[phrase](url)`. Hard-fail on a miss: `if phrase not in md: raise SystemExit("ANCHOR MISS")`. This immediately caught a bad anchor — "Shropshire Fire and Rescue" was never in the text; the real sentence was "Firefighters responded quickly to the emergency."
3. **Harvest internal URLs live, never invent them** — one batched shell loop of `GET /wp/v2/posts?search=<topic>&per_page=3&_fields=link,title` with `sleep 1` across all thin topics. The site's post-search is fuzzy: "zoo fire" returned an Indonesian earthquake and an Australian alert system; take the one real match and drop the rest rather than linking something unrelated.
4. External additions should be primary/authoritative (`gov.uk`, `ahdb.org.uk`, `studentaid.gov`, `consumerfinance.gov`, the relevant fire/rescue service).

## Handling a `**bold**` / nested-bracket markdown body
Two `md2html` guards beyond the plain link regex, both hit this session:
- **Malformed nested link** `[[text](url)]` appears in hand-edited bundles and renders as stray brackets. Unwrap first: `re.sub(r"\[\[(.*?)\]\((.*?)\)\]", r"[\1](\2)", line)` before the normal link substitution.
- Convert `**bold**` → `<strong>` *after* links, and wrap every non-empty line in its own `<p>`.

## Revision cycles: a CORRECTED package arrives AFTER you already published
This user works in successive revisions of the same batch (`STAGE_4_5_...` → `FINAL_STAGE_4_5_..._FULLY_VERIFIED.md` → `FINAL_ALL_14_..._CORRECTED_VERIFIED.md` + a `PUBLICATION_READY_CHECKLIST.md` / `MASTER_DELIVERY_INDEX.md`). Expect a newer file to land *after* the batch is live, with "these are manually fact checked, update any stories that are on WordPress now." Handle it as an UPDATE pass, not a re-publish.

1. **Use ONLY the newest named file.** They may say so explicitly ("DONT PUBLISH ANYTHING FROM THE PREVIOUS DOC"). Never merge bodies across revisions — older revisions carry the uncorrected facts.
2. **UPDATE in place via `POST /wp/v2/posts/<id>`** with corrected `title`, `content`, `excerpt`, `categories`, `tags`; then the usual `PUT ...?context=edit` for the Yoast trio. Keep the slug→post-id map from your publish run so you can find each one. Articles missing from the earlier revision get published fresh in the same script, scheduled a few minutes out with the usual random gaps.
3. **KEEP THE ORIGINAL SLUGS on already-live posts.** The corrected file will carry new slugs (`...-thameslink-capacity-2026` replacing `...-safety-crisis-2026`). Live posts are already indexed — changing the slug 404s the existing URL. Keep the published slug, *tell the user you did and why*, and offer the swap-with-redirect as their choice. Only genuinely-new articles take the file's slug.
4. **VERIFY THE CORRECTIONS LANDED IN THE LIVE BODY** — a 200 from the POST proves nothing about content. Re-GET `?context=edit` and grep `content.raw` for a distinctive token per correction, printing a `{token: True/False}` dump:
   `{271573:['Thameslink','176 percent'], 271577:['2013','extremely limited'], 271579:['Sweet v. McMahon'], 271585:['drought','driest July']}`
   This is cheap and is the only proof the corrected text is actually on the page. (2026-08-05: all passed except a `370,000` figure that lived only in the meta description, not the body — worth reporting as a consistency gap rather than silently ignoring.)
5. **The corrections are often causation-level, not typo-level** — worth calling out in the hand-off. That batch reversed UK-harvest causation entirely (wet spring/heavy rain → **drought and record heat, driest July in nearly two centuries**), swapped a train operator (Southern Railways → **Thameslink**, 150-180% → measured **176%**), named an unnamed settlement (**Sweet v. McMahon** borrower-defense), moved a first-identification date (2016 → **2013**), and deleted a wholly fictitious project (a 14MW Rome BESS that did not exist). Publishing the pre-correction text would have shipped visibly wrong stories.

### Stripping correction markers out of a `_CORRECTED_` file before publishing
A corrected package annotates its own edits inline, and those annotations MUST NOT reach the published body. Strip them in the markdown, before `md2html`:
```python
body = re.sub(r"\*\*CORRECTED[^:*]*:\*\*\s*", "", body)     # **CORRECTED SECTION:** / **CORRECTED INTRODUCTION:**
body = re.sub(r"\*\*REMOVED[^.*]*\.?\*\*\s*", "", body)      # **REMOVED INCORRECT OWNERSHIP CLAIM.**
body = re.sub(r"\*\*[A-Z][A-Z /]+SECTION:\*\*\s*", "", body) # **CORRECTED GRAVITY IMPACT SECTION:**
```
Also note the heading in these files is `### CONTENT WITH CORRECTIONS` / `### CONTENT (VERIFIED - NO CORRECTIONS NEEDED)`, not a bare `### CONTENT` — match `### CONTENT[^\n]*\n` or your parser finds zero bodies. Run the structural grep and a field dump (`n | body? | title? | slug?`) across all N articles before publishing; 14/14 should report a body.

## Composing metadata yourself when the bundle's is thin
When the bundle supplies "Combined Title **Options**" (2–3 per article) rather than one title, pick/compose ONE — prefer a specific, number-carrying headline — and use it for both `title` and `_yoast_wpseo_title`. Same for meta: measure `len()` and keep ≤200 (the bundle's own count line lies — see Pitfalls). Tags: take 4 from the bundle's 5, dropping the most redundant. Declaring all of this as an explicit `ART = [dict(...), ...]` table in one script (rather than regex-parsing a loose markdown file) sidesteps the entire class of blank-title/blank-meta parse traps and is the preferred shape for a ≤20-article batch.

## Pitfalls
- **Source contradiction:** draft said "15 injuries, fractured arm, full refund, 8,500 units, Amazon-exclusive" but its own cited CPSC page said 2 minor injuries, free repair kit, 47,166 units, sold on Harppababy.com AND Amazon, ~$130. Published CPSC-accurate version; user accepted. Rule: when draft and its own primary source disagree, the source wins — flag and correct.
- **Phantom categories/tags:** requested categories (e.g. "Product Recalls", "Wildfire", "Retirement") often don't exist. Pull the real list; map to existing; never invent. **"Don't add new categories" is category-specific — it does NOT forbid creating tags.** When the user forbids new categories but supplies custom tags, pull the live tag list and CREATE the missing tags via `POST /wp/v2/tags` (allowed). Verified this session: 23 fresh tags created cleanly while 0 categories were invented. Map each requested category name → nearest existing category by meaning (e.g. "Climate Crisis"→`climate`, "Urban Emergency"→`disaster`, "California Law Enforcement"→`crime`, "Health & Safety Warning"→`health`); build a `requested_name → existing_slug` table and resolve to IDs, never trust the literal name.
- **Dead internal links:** user-supplied internal links frequently 404. Use the sitemap to find real topically-related live URLs; do not fabricate replacement links.
- **Self-reported char counts lie.** A "package" file may label its meta descriptions as "198 chars ✅" while the actual string is 214–224 (the source undercounted, often excluding spaces or truncating). Always measure the real length and TRIM to the user's stated cap (e.g. ≤200) before publishing — don't trust the bundle's own count line. Concrete case: in the 2026-08-05 `FINAL_16_STORIES_WITH_EMBEDDED_LINKS.md` batch, every meta labeled "(200 chars)" actually measured 214–250. Publish verbatim only if the user explicitly wants the file as-is; otherwise trim to ≤200 (Yoast truncates the SERP snippet anyway, but oversized metas look unprofessional and can trip SEO audits).
- **Throttle batch POSTs.** Cloudflare/WP can choke on a tight burst of 6 publish POSTs. Insert a `time.sleep(3)` between posts (and between meta-creation POSTs) to avoid spurious 403/429.
- **A `future` (scheduled) post 404s on its public URL — that is NOT a failed assignment or a broken publish.** When verifying a mixed backdated/scheduled batch, the not-yet-released posts return HTTP 404 on `/slug/` and their hero token greps to 0 occurrences, because the page does not exist publicly yet. Do not "fix" this or report it as a failure. **Distinguish before alarm:** re-GET via the REST API with `&status=publish,future,draft` — if `featured_media` holds the right id and `status` is `future`, the work is correct and will render on release. Confirm by comparing the post's `date_gmt` against the SERVER clock (`curl -sI https://www.karmactive.com/ | grep -i '^date'`), not your local clock. 2026-08-05: the SpaceX post greped 0 hits for `FALCON` purely because it was scheduled for 13:44 UTC while the server read 12:34 UTC; the DB assignment was already correct. Rendered-hero verification is only meaningful for posts whose time has passed.
- **Include `&status=publish,future,draft` on every verification GET in a scheduled batch.** The default REST query returns only published posts, so a plain `?slug=` lookup on a scheduled post comes back as an empty array and your audit reports "MISSING" for a post that exists and is fine.
- **Lazy-loaded hero images — read `data-src`, not `src`.** The rendered article hero `<img class="...wp-post-image...">` almost always contains `src="data:image/svg+xml..."` (a 1×1 placeholder) and the real URL in `data-src=".../yourfile.webp"`. A verification script that greps only `src=` will conclude the wrong image is showing and false-alarm a FIFU override. Always match the FIRST `wp-post-image` img's `data-src` against your uploaded file path.
  - **Simplest reliable rendered-hero check:** curl the page to a file, then `grep -c '<distinctive-filename-token>'` (e.g. `RBI-Tower`, `Indonesias-B50-Biodiesel`). A count ≥1 means the hero is yours — this sidesteps brittle attribute-order regexes entirely. A multi-stage pipe like `grep -o 'wp-post-image[^>]*' | grep -oE '(data-src|src)="..."'` silently returns EMPTY when the class list runs long or the attribute order differs, which reads as a failure when nothing is wrong. Grep for the filename token, not the tag structure.
- **HTML-escaped meta comparison false-negatives.** When verifying the Yoast `<meta name="description">` on the public page, apostrophes become `&#039;` and curly quotes `&#8220;`/`&#8221;`. Comparing the raw stored string (e.g. "Mae D'Agostino") against the page HTML will NOT match and falsely report "meta missing." `html.unescape()` the page fragment before comparing, or compare only the first ~40 chars which are usually unescaped.
- **FIFU override is conditional, not automatic.** On karmactive, REST `featured_media` assignment renders correctly for any post that had NO prior featured image — the hero `wp-post-image` serves your upload. FIFU only hijacks the hero when the post already has a `_fifu_image_url` set (i.e. you are re-assigning an image on a post that already used FIFU). So: after assigning, check the FIRST `wp-post-image data-src`; if it equals your file, declare done. Only treat it as a FIFU problem when the hero shows a DIFFERENT file.
- **Preserve original paragraph structure — NEVER collapse newlines.** A multi-article "package" file almost always has ONE paragraph per source line. Wrap each non-empty line in its own `<p>` tag. NEVER do `body.replace("\n"," ")` or `.join()` the lines — that merges the entire article into one giant unreadable paragraph and destroys the original layout (this bit us this session; it required a separate full re-PUBLISH to fix, after the post was already live). In the DRY-RUN, print the per-article paragraph count and confirm it matches the source line count; if it shows 1 paragraph, the parser is wrong — fix it BEFORE publishing.
- **MSYS/Windows subprocess + curl = path breakage.** Running `curl` via `subprocess.run(["curl",...])` in a `.py` script silently produced EMPTY responses (upload "failed" with no error) because MSYS mangled the `@/c/Users/...` file path. **Fix / lesson:** prefer a native `bash` script with hard-coded `cd` into the folder containing the images, OR run `curl` directly in the terminal tool. If you must use Python, pass the file path resolved against an already-cd'd working dir, not an absolute MSYS path inside subprocess args.
- **Long/comma filenames + transient HTTP:000 drops.** A valid WebP (`Aaykar_Bhavan,_Income_Tax_Department,_Pune.webp`) repeatedly returned empty `HTTP:000` (dropped connection) while short-named files succeeded. **Fix:** copy the file to a short name (e.g. `incometax.webp`) and retry; also wrap uploads in a 3–5× retry loop with `sleep 2` between attempts. HTTP:000 is a transient drop, not a permanent block.
- **Filename ≠ subject for user-dropped social-media files.** When the user downloads a Facebook/IG photo and drops the file, the filename is an opaque numeric ID and may not correspond to the article you'd guess. The only safe mapping is `vision_analyze` the file and assign by what it depicts. This session a Krishi-Bhavan-post-ID-named file was actually the NJ-police shrub photo — assigning by filename would have put the wrong image on the wrong post. Always vision-verify before `featured_media` assignment.
- **Never inline a throwaway `python -c "..."` for image/Commons work — write a small `.py` file instead.** Two independent failures this session, both avoided by a 10-line file:
  - A `python -c` whose body contained `\x00` (the anchor-masking trick) was rejected before execution with `ValueError: open: embedded null character in path` — a *pre-flight guard* choked on the null byte in the command string, so the code never ran and the error named a path problem that did not exist.
  - Quoting: any inline snippet containing apostrophes, `°`, or nested quotes breaks the shell/`-c` boundary unpredictably (see the JSON note below).
  Re-sourcing one image took five iterations; each was a two-line edit to `kx_r5.py` plus a re-run, which is faster and leaves an artifact you can diff.
- **`by_title()` on Commons returns `thumb: None` for a title you typed by hand.** Commons titles are long and lossy to retype — the backpack file's real title ran to 180 characters ending `...100825-M-PC721-030.jpg`, and the shortened guess silently returned a page stub with `thumb: None` rather than an error. **Fix: never hand-type a Commons title. Re-run the `search()` that surfaced it and filter by a distinctive fragment** (`[x for x in search(term, 10) if "Hone Creek" in x["title"]]`), then use that object's `thumb`.
- **Filter `if x["w"] >= x["h"]` in search output when you need a hero image.** Commons returns many portrait phone photos unusable as a wide featured image; filtering in the print loop stops you evaluating candidates you would reject anyway.
- **Don't embed JSON with quotes inside a shell `-c` / heredoc.** Alt-text containing apostrophes (e.g. "India's 50 Lakh...") breaks inline `python -c "json.dumps('...'s...')"` with `SyntaxError: unterminated string literal`. **Fix:** serialize JSON in a real Python script (`json.dumps(...)`), never by hand-concatenating a quoted string into the command.
- **"AUTH FAILED / empty response" is often a missing URL in the curl args, NOT a credential problem.** When building the REST call inside a helper (e.g. `api(method, path)`), it is easy to append the headers but forget to append the actual `url` (`f"{W}/{path}"`) to the `args` list. curl then exits `RC:2 "no URL specified"` and returns empty → your auth check sees `{"_raw":""}` and prints "AUTH FAILED" even though creds are fine. **Symptom:** a direct `curl -H "Authorization: Basic ..." <url>` in a heredoc works, but the script's identical-looking call returns empty. **Fix:** make the URL an explicit positional element of the args list (`args = [..., url]`), and when debugging, capture + print **stderr and returncode** (curl's "no URL specified" goes to stderr, so `capture_output=True` without reading `p.stderr` hides it). Gate the dump behind an env flag like `DEBUG_CURL=1` that prints `CMD / RC / ERR`. Do NOT rely on a closure or `f"{W}/{path}"` being implicitly sent.
- **Transport flakiness is a SECOND empty-response cause, distinct from the missing-URL bug.** Even with the URL and credentials correct, the FIRST REST call against karmactive's Cloudflare front sometimes returns an empty body (cold-TLS / first-byte drop) — `curl` exits 0 with no output, so auth checks see `{"_raw":""}` and wrongly print "AUTH FAILED." **Fix:** bake retry + timeouts into the curl base args so a transient empty response is retried at the transport layer: `base=["curl","-s","--retry","5","--retry-delay","2","--connect-timeout","20","--max-time","60","-A",UA]`. This eliminated the intermittent empties in the 2026-08-05 batch; without it, the publish/fix scripts fail on the very first `users/me` call. (Keep the python-level loop as a backstop for JSON-parse failures only — do NOT also re-send the same empty at the python layer; the curl `--retry` handles the transport drop.)
- **Blank TITLE is a `**TITLE OPTIONS:**` parse trap — verify every title is non-empty BEFORE publishing.** A package file often puts the choices on LATER lines, e.g. `**TITLE OPTIONS:**` on one line then `1. (120 chars) The Real Combined Title …` on the next. A loose regex that grabs only the `**TITLE OPTIONS:**` line (or reads `**TITLE OPTIONS:**` as the title) yields an EMPTY title — and WordPress happily publishes a post with no title, which is what happened to all 16 posts in the 2026-08-05 `FINAL_16_STORIES_WITH_EMBEDDED_LINKS.md` batch. Parse the option line(s) AFTER the label, prefer the `(120 chars)` combined title (option 1), and in the DRY-RUN fail loudly if any title is empty. Same trap hits **META DESCRIPTION**: the text usually sits on the line AFTER `**META DESCRIPTION (200 chars):**`, so grabbing only the label line yields empty meta. Read the label's NEXT non-empty line.
- **Yoast focus keyphrase / meta description must be PUT, but ALSO must be read from the FILE — they are separate fields, not the excerpt.** The 2026-08-05 batch shipped with all 16 Yoast `_yoast_wpseo_metadesc` and `_yoast_wpseo_focuskw` BLANK because the publish script set only the WP `excerpt` + used its own category guessing and never carried the file's `**META DESCRIPTION**` / `**FOCUS KEY PHRASE**` into the `PUT /posts/<id>?context=edit` meta block. Fix: parse `FOCUS KEY PHRASE` (same-line `**FOCUS KEY PHRASE:** value`) and `META DESCRIPTION` (next-line text), then in the post-publish `PUT` send `{"meta":{"_yoast_wpseo_metadesc":<meta>,"_yoast_wpseo_focuskw":<fk>,"_yoast_wpseo_title":<title>}}`. (Setting `excerpt` is fine but does NOT populate Yoast's description — they are different.)
- **Stray "Word Count: N words | Category: X" line leaks into the published body.** A package file often appends a footer/summary line like `**Word Count: 350 words | Category: Travel/Airlines**` after the body. If the parser preserves the whole markdown block as `content`, that line publishes as a literal paragraph at the top/bottom of the article — looking unprofessional. Detect it with a regex like `<p>\*{0,2}Word Count:.*?</p>` and STRIP it before publishing. The user's preferred replacement for it — now a STANDING instruction — is an **"Estimated reading time: N minutes"** line at the top (compute N = max(1, round(wordcount/200))), which reads far better than a raw word-count/category footer. This session the user explicitly said: "rather than having word count and categories in the beginning of the article please have the time that takes to read the complete article." Never publish the literal footer; always strip it and prepend the reading-time estimate as the very first paragraph. Compute N from the article's ACTUAL word count (count words in the body), not by echoing the file's self-reported "Word Count" line, which is unreliable. This session the 16-post batch shipped with the literal footer on every article; a follow-up `fix_readtime.py` removed the line and prepended the reading-time estimate. Bake both (strip + replace) into the publish/fix script so it never ships.
- **Use the FILE's explicit `**CATEGORIES:**` field — do NOT substitute your own subject-fit mapping.** When the user hands you a package file WITH per-article categories, those are authoritative. The 2026-08-05 batch had all 16 categories WRONG because the agent guessed by topic (e.g. filed Jetstar under `aviation`) instead of reading the file's `**CATEGORIES: Business, Transportation**`. The per-author category buckets (sunita: business/policy/social-welfare, etc.) are ONLY for picking the AUTHOR (see Author assignment), never for the post's categories. Exception: if a file category does not exist on the site and the user said "don't add new categories," map it to the NEAREST existing category (e.g. file `Transportation` → site `public-transportation` 12397 on karmactive) — and tell the user you mapped it.
- **When you rewrite a body from a primary source, define the override AFTER the parse loop, not inside the article table.** The Ukrop's rewrite this session was injected as `bodies["11"] = """..."""` placed *after* the file-parse block and *before* the build loop — that ordering is what makes it win over the parsed text. Update `title`, `slug` and `meta` in the same commit (a slug promising `class-1-fda-alert` is wrong once you learn it's FSIS), and re-run `DRY=1` to confirm the new paragraph/word/link counts. Publishing the corrected body with the stale slug is a half-fix.
- **MANDATORY post-publish field audit (this class of task fails silently).** After any multi-article publish, re-GET every post (`?context=edit`) and assert, per post: `title` non-empty, `_yoast_wpseo_metadesc` non-empty, `_yoast_wpseo_focuskw` non-empty, `_yoast_wpseo_title` non-empty, `categories` equal the file's mapped IDs, and body `content` contains embedded `href=` links. The 2026-08-05 batch looked "done" (16 green OK lines) but a re-audit exposed all titles + all Yoast fields blank and all categories wrong. A scripted audit that prints a per-post `TITLE? Ymeta Yfoc Ytitle CATS(live) Nlinks` table is the only reliable way to catch this — do NOT trust the publish script's own "OK" output. Reusable: `scripts/audit_published.py`.

## Verification
GET each post back (`?context=edit`): confirm `status:"publish"`, correct `slug`, `categories`, `tags`, and PARAGRAPH COUNT in `content.rendered` matches the source. `curl -o /dev/null -w "%{http_code}"` the public `/slug/` → expect 200. Yoast meta IS set via PUT (see gotchas) — confirm it persisted by re-reading `?context=edit` meta AND by fetching the public `/slug/?nocache=1` and grepping for `<meta name="description">` (the live `<head>` is the real proof it's serving to search engines). When grepping the rendered `<meta name="description">`, HTML-unescape the comparison string first (apostrophes render as `&#039;`, curly quotes as `&#8220;`) — otherwise a valid meta falsely negatives (this session an article with "Mae D'Agostino" was falsely flagged because the apostrophe was escaped). For the featured-image hero, the article `<img>` is usually **lazy-loaded**: the real URL is in `data-src`, not `src` (the `src` holds a 1×1 SVG placeholder). Match the FIRST `wp-post-image` img's `data-src` against your uploaded file path — matching means the hero is correctly yours.
